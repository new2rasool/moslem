# ماژول ۱۱ — فرایند توسعه: مراحل طراحی و نوشتن سورس ربات مدیریت گروه (Development Workflow)

این سند پاسخ این پرسش است: «اگر بخواهیم از صفر سورس ربات را بنویسیم، **به ترتیب چه کارهایی** انجام
می‌دهیم و **بخش‌ها را چطور از هم جدا** می‌کنیم؟» — یک نقشهٔ مهندسی گام‌به‌گام، مستقل از سندهای
قابلیتی (ماژول‌های ۱ تا ۱۰).

---

## ۰. اصل پایه: «ابتدا مرزها، بعد محتوا» (Separation First)

قبل از نوشتن حتی یک هندلر، **مرزهای منطقی کد** را مشخص می‌کنیم تا هر بخش مستقل قابل توسعه، تست و
تعویض باشد:

### ۰.۱. مرز لایه‌ای (Layered Boundaries) — جداکردن از پایین به بالا
```
┌─────────────────────────────────────────────────────────┐
│  لایهٔ ۱: Presentation (Handlers) — فقط ورودی/خروجی تلگرام │  ← نازک، بدون منطق
├─────────────────────────────────────────────────────────┤
│  لایهٔ ۲: Application (Services/Use-cases) — منطق کارها    │  ← مستقل از تلگرام
├─────────────────────────────────────────────────────────┤
│  لایهٔ ۳: Domain (Entities + قواعد ناب) — قلب قوانین       │  ← خالص و بدون وابستگی
├─────────────────────────────────────────────────────────┤
│  لایهٔ ۴: Infrastructure (DB/Redis/API خارجی/زمان‌بند)      │  ← قابل تعویض
└─────────────────────────────────────────────────────────┘
```

**قانون طلایی جهت وابستگی (Dependency Rule):**
هر لایه فقط می‌تواند به لایهٔ پایین‌تر خود وابسته باشد. هندلر ← سرویس ← دامنه؛
هیچ‌کس به هندلر وابسته نیست. دامنه هیچ‌چیز از Pyrogram/Telegram نمی‌داند.

### ۰.۲. مرز برش عمودی (Vertical Slices) — جداکردن بر اساس قابلیت
هر «قابلیت» (مثل CAPTCHA) یک برش عمودی است که از همهٔ لایه‌ها رد می‌شود:

```
feature/captcha/
├── handlers/captcha.py        ← لایهٔ ۱ (دکمه‌ها، پیام‌ها)
├── services/captcha_service.py ← لایهٔ ۲ (زندگی یک چالش: ساخت/تصدیق/انقضا)
├── domain/captcha.py           ← لایهٔ ۳ (تولید پرسش، بررسی پاسخ — توابع خالص)
└── repositories/captcha_store.py ← لایهٔ ۴ (ذخیرهٔ وضعیت در Redis)
```

> **ترکیب هر دو مرز:** اسکلت لایه‌ای ساخته می‌شود (فاز ۱–۲) و سپس قابلیت‌ها **یکی‌یکی به‌صورت
> برش عمودی** روی آن سوار می‌شوند (فاز ۳). به این ترتیب هر قابلیت «کامل و قابل تحویل» است.

### ۰.۳. مرزهای افقی دیگر (که باید از روز اول جدا باشند)
| مرز | چرا جدا؟ |
|---|---|
| `config` (محیط/رمزها) | تغییر در استقرار بدون تغییر کد |
| `i18n` (رشته‌های متنی) | افزودن زبان بدون دست‌زدن به منطق |
| `logging/observability` | رفع اشکال در تولید بدون دست‌زدن به کد |
| `models/db` از `services` | تعویض SQLite→PostgreSQL بدون بازنویسی منطق |
| `client` (ابزار تلگرام) از `handlers` | آپگرید Pyrogram یا تعویض کتابخانه در یک نقطه |
| `tests` | هر لایه جدا تست شود (هرم تست) |

## ۱. انتخاب استک فناوری (تصمیم‌های از پیش) — ورودی فاز ۰

| لایه | انتخاب پیشنهادی | دلیل |
|---|---|---|
| زبان/زمان‌اجرا | Python 3.11+ / asyncio | اکوسیستم تلگرام، سادگی |
| کتابخانهٔ تلگرام | Pyrogram v2 (MTProto) | پشتیبانی کامل از مدیریت گروه (برخلاف Bot API محدود) |
| DB رابطه‌ای | PostgreSQL (توسعه: SQLite با لایهٔ Repo یکسان) | JSONB برای تنظیمات، ایندکس‌ها |
| کش/حالت زودگذر | Redis | TTL برای ضد سیل/کپچا/کش |
| زمان‌بند | APScheduler (AsyncIO) | تایمرها و تسک‌های شبانه |
| مهاجرت DB | Alembic | تغییر Schema کنترل‌شده |
| پیکربندی | pydantic-settings + `.env` | اعتبارسنجی هنگام بوت |
| تست | pytest + pytest-asyncio + vcr/رسانک | هرم تست |
| کیفیت | ruff + mypy + pre-commit | استاندارد یکدست |
| استقرار | Docker Compose → (بعداً) چند نمونه | انتقال آسان |

**تصمیم‌های کلیدی که باید قبل از کد نویسی نهایی شوند (ADRs):**
1. پیشوند دستورها (`/`, `!`, فارسی) — یک پیش‌پردازش‌گر متمرکز.
2. مدل نقش‌ها: نقشِ «رباتی» (در DB خودمان) + نقشِ «تلگرامی» (اختیاری) — دو بعد مستقل.
3. Policy ذخیره‌سازی: کدام داده در SQL، کدام در Redis، کدام هرگز (متن پیام‌ها).
4. ترتیب پایپ‌لاین بررسی پیام (ماژول ۲.۱۰) — به‌صورت لیست پیکربندی‌شونده، نه if زنجیره‌ای.

## ۲. فازبندی توسعه (Phases) — هر فاز: هدف، کارها، خروجی، شرط خروج

### فاز ۰ — آماده‌سازی محیط و زیرساخت پروژه (نیم‌روز)
- ساخت ریپو، `pyproject.toml`، محیط مجازی، `pre-commit`، CI خالی (lint+test).
- `.env.example` + مستند INSTALL.
- ساختار پوشه‌ها (بخش ۴) + `README` نقشهٔ پروژه.
- ساخت اکانت ربات تست (BotFather) + **گروه آزمایشی** با ۳ اکانت تستی.
- **خروجی:** `git init` کامل، `make setup` اجرا می‌شود، ربات با توکن به تلگرام وصل و لاگ می‌دهد.

### فاز ۱ — اسکلت هسته (Core Skeleton) (۱–۲ روز)
اولین کد واقعی — **بدون هیچ قابلیتی**، فقط ستون‌فقرات:
- [ ] `config.py` (pydantic-settings) + بوت‌سکانس (startup: اتصال DB/Redis، تست اتصال، ثبت هندلرها)
- [ ] `client.py`: ساخت Pyrogram app + مدیریت shutdown تمیز + هندلر خطای سراسری (`safe_handler`)
- [ ] `logging.py`: لاگ ساختاریافته (JSON در prod) + `logger.exception` مرکزی
- [ ] لایهٔ `db`: اتصال + **جداول پایه** (`groups`, `users`, `group_roles`) + Alembic اول
- [ ] سرویس `access`: بارگذاری OWNER/SUDO از env، تابع `level_of(chat, user)` — خروجی: ۰..۴
- [ ] `i18n`: پوشهٔ `locales/fa` و `en` + تابع `t(key)` + نمونه `ping`
- [ ] هندلرهای نمایشی: `/start`, `/ping`, `/help` (فارسی+انگلیسی)
- **شرط خروج (DoD):** `pytest` سبز (تست access، تست config)؛ ربات روی گروه آزمایشی `/ping` جواب می‌دهد؛ لاگ خطا کار می‌کند.

### فاز ۲ — لایه‌های میانی و ابزار مشترک (۲–۳ روز)
زیرساخت‌هایی که همهٔ قابلیت‌ها بعداً از آنها استفاده می‌کنند:
- [ ] `middleware` سه‌تکه: `PermissionMW` (سطح دسترسی) ← `AntiFloodMW` (نرخ ورودی) ← `Pipeline` (ترتیب بررسی پیام)
- [ ] `command_router`: نگاشت یکدست «فارسی/لاتین/پیشوند» به یک تابع (جداول `COMMANDS`)
- [ ] `repositories` الگو: `GroupRepo`, `UserRepo`, `RoleRepo` (اینترفیس → پیاده‌سازی SQL)
- [ ] کش تنظیمات گروه (درون‌حافظه + TTL) با `get_group(chat_id)` واحد
- [ ] `utils`: `parse_duration` («1d6h» → ثانیه)، `normalize_text` (۶ مرحلهٔ ماژول ۲.۳)، `parse_target` (ریپلای/@/id)
- [ ] `callbacks/router`: مسیریابی امن دکمه‌ها با prefix و اعتبارسنجی `chat_id/user_id`
- [ ] سازوکار **Undo/Replay**: ثبت اکشن‌ها در Redis برای «خنثی‌سازی ۱۰ دقیقه‌ای»
- **شرط خروج:** تست‌های unit برای هر util؛ دموی «یک قابلیت قلابی» که از همهٔ لایه‌ها رد شود (ثبت در DB + پاسخ دکمه‌ای) تا صحت اتصال لایه‌ها اثبات شود.

### فاز ۳ — توسعهٔ قابلیت‌ها به‌صورت برش عمودی (به ترتیب وابستگی)
> ترتیب زیر از **وابستگی منطقی** پیروی می‌کند: هر قابلیت به قابلیت‌های بالایی‌اش نیاز ندارد.
> هر آیتم = یک برش عمودی کامل (handlers+service+repo+test+i18n+doc).

| # | قابلیت (برش عمودی) | وابسته به |
|---|---|---|
| 1 | مدیریت نقش‌ها: promote/demote/سطح‌بندی | فاز ۱–۲ (access) |
| 2 | ابزار پایه: `del/purge/pin/kick/mute/ban/tban` (+تایمرهای آزادسازی) | نقش‌ها |
| 3 | رویدادهای عضو: خوش‌آمد/خداحافظی/قوانین (+گیت قوانین) | ابزار پایه (restrict) |
| 4 | فیلتر کلمات و لینک + `normalize` | utils فاز ۲ |
| 5 | ضد سیل (پنجرهٔ لغزان) | ابزار پایه |
| 6 | CAPTCHA + سپر اکانت تازه | رویداد عضو |
| 7 | ضد راید + قفل ورود | CAPTCHA + ضد سیل |
| 8 | GBan/CAS | نقش‌ها |
| 9 | سیستم هشدار + گزارش ناشناس | ابزار پایه + نقش‌ها |
| 10 | قفل‌های کامل محتوا (ماژول ۵) | فیلترها + ضد سیل |
| 11 | فیلترهای سفارشی/نوت‌ها/پاسخ خودکار | فیلتر کلمات |
| 12 | کانال لاگ و حسابرسی | همه (قلاب‌های لاگ از قبل) |
| 13 | آمار و نمودار | (شمارنده از فاز ۲) |
| 14 | زمان‌بندی (تایمر) | فاز ۱ scheduler |
| 15 | پنل مالک: broadcast/federation/backup | همهٔ بالا |

**قانون هر برش عمودی:** یک قابلیت = یک PR؛ هر PR باید تست + i18n + لاگ + مستند کوتاه داشته باشد؛
تا DoD نگذرد، سراغ بعدی نرویم. (قابلیت‌های ۳ و ۶ را می‌توان با «برش افقیِ» موقت دمو کرد.)

### فاز ۴ — سخت‌سازی (Hardening) (۲–۳ روز)
- [ ] شبیه‌سازی خطاها: قطع Redis/DB، ارسال به گروهی که ربات اخراج شده، 429 واقعی
- [ ] پیاده‌سازی «صف ارسال» و Retry با Backoff (ماژول ۱۰.۲)
- [ ] تست Idempotency: دوبار رسیدن رویداد ورود (Telegram گاهی تکراری می‌فرستد) → بدون دو کپچا
- [ ] پاکسازی رخ‌دادهای بازمانده بعد از ریاستارت (کپچاهای نیمه‌کاره، تایمرها)
- **خروجی:** ۵ سناریوی Chaos تست‌شده، مستند «رفتار در خطا».

### فاز ۵ — عملکرد و مقیاس (۲ روز)
- [ ] انتقال مسیرهای داغ به Redis (شمارنده‌ها، flood) + بنچمارک (هدف p95 < 400ms)
- [ ] Batch-insert آمار · aggregate شبانه · retention
- [ ] (اختیاری) معماری چندنسخه با Pub/Sub — فقط اگر > ۱۰۰ گروه هدف است
- **خروجی:** گزارش بار ۵۰ پیام/ثانیه بدون افت.

### فاز ۶ — استقرار و بهره‌برداری (۲ روز)
- [ ] Dockerfile + docker-compose (bot/redis/postgres) + healthcheck
- [ ] systemd یا orchestration؛ `.env` تولید؛ بکاپ خودکار (pg_dump + `restore.sh`)
- [ ] مانیتورینگ: لاگ مرکزی + هشدار «ربات down» + متریک‌های داخلی
- **خروجی:** مستند RUNBOOK (نصب، آپگرید، بازیابی، عیب‌یابی).

### فاز ۷ — پذیرش (QA) و تحویل
- [ ] چک‌لیست پذیرش از «پیوست ب» سند اصلی (هر ۱۲ بند)
- [ ] تست E2E روی گروه آزمایشی با سناریوهای واقعی (ورود ربات/کپچا/بن/…)
- [ ] مستند کاربر نهایی + مستند مدیر + مستند توسعه‌دهنده
- **خروجی:** نسخهٔ v1.0 تگ می‌شود.

## ۳. استراتژی پیاده‌سازی تدریجی (شروع ساده، تکامل تدریجی)

بهجای «همه‌چیز در یک نسخه»، سه افق تعریف می‌کنیم:
1. **افق ۱ (جاری):** اجرای تک‌پروسه روی SQLite + Redis اختیاری (شروع سریع).
2. **افق ۲ (چند روز بعد):** PostgreSQL + Alembic + Redis اجباری.
3. **افق ۳ (فقط در نیاز واقعی):** چند Worker + صف‌ها.

> همه‌چیز از روز اول **پشت اینترفیس** (Repository/Scheduler/Cache) نوشته می‌شود تا افق‌های ۲ و ۳
> بدون بازنویسی منطق ممکن شوند. این «جداسازی» مهم‌ترین تصمیم معماری است.

**قواعد ساختار:**
- هر پوشه فقط یک مسئولیت؛ نام‌گذاری بر اساس «قابلیت» در handlers و «لایه» در services/domain.
- بدون «پوشهٔ utils سراسریِ بزرگ» — utils به‌اندازهٔ ماژول کوچک می‌ماند.
- import فقط رو به پایین (هیچ هندلری از هندلر دیگر import نمی‌کند؛ از سرویس import می‌کند).

## ۵. تعریف «تمام‌شده» برای هر بخش (Definition of Done)

یک قابلیت وقتی «تمام» است که همهٔ اینها سبز باشند:
1. **کد:** هندلر نازک + سرویس + تست؛ بدون import چرخه‌ای؛ ruff/mypy پاس.
2. **تست:** unit برای دامنه (۱۰۰٪ منطق ناب) + integration برای سرویس.
3. **i18n:** همهٔ رشته‌های جدید در `fa` و `en` (تست «رشتهٔ گمشده» در CI).
4. **لاگ:** رویدادهای لازم در audit ثبت می‌شوند (اگر قابلیت لاگ‌پذیر است).
5. **مستند:** یک پاراگراف در docs/feature-xyz + نمونه دستور.
6. **تست دستی:** سناریوی چک‌لیست در گروه آزمایشی انجام و تأیید شده.

## ۶. استراتژی تست (هرم تست — از پایین)

| سطح | چی؟ | کجا؟ | سرعت |
|---|---|---|---|
| Unit | domain خالص: flood، normalize، duration، captcha math، سطوح دسترسی | محلی، بدون شبکه | میلی‌ثانیه |
| Integration | service + repository با DB تست (SQLite/Postgres تستی) و Redis فیک | CI | ثانیه |
| Contract | رسانک (VCR) پاسخ‌های Pyrogram برای هندلرها — بدون تماس با تلگرام | CI | ثانیه |
| E2E | سناریوی کامل روی گروه واقعی آزمایشی (علامت `@slow`) | دستی/شبانه | دقیقه |

- **فیکسچر مرکزی:** ساخت کاربر/گروه تستی، `make_user(level=…)`.
- معیار: پوشش ≥ ۸۰٪ در domain و services؛ هندلرها نازک‌اند (پوشش کمتر مجاز است).

## ۷. ترتیب کارهای روزانه در عمل (روتین توسعه)

```
۱) انتخاب ۱ کارت از بک‌لاگ (کوچک، با DoD)
۲) ساخت شاخه: feature/captcha-basic
۳) پیاده‌سازی برش عمودی (domain ← service ← handler ← i18n ← لاگ)
۴) تست unit/integration همان کارت + اجرای کل pytest
۵) PR + ریویو (تمرکز: مرز لایه‌ها، i18n، حالت‌های لبه)
۶) merge → CI → دیپلوی به گروه آزمایشی → تست دستی → بستن کارت
```

---

## ۸. ریسک‌ها و کاهش آن‌ها (پیش از شروع کدنویسی بدانیم)

| ریسک | کاهش |
|---|---|
| تغییرات breaking در Pyrogram | جداکردن client پشت یک لایه؛ پین نسخه؛ تست smoke پس از آپگرید |
| 429 / محدودیت MTProto | صف ارسال از روز اول؛ هرگز `send` مستقیم در هندلرها در مسیر داغ |
| Scope creep (کشیده‌شدن دامنه) | هر ایده → کارت جدید؛ MVP افق ۱ شامل فقط ۸ قابلیت است |
| ری‌فکتور پرهزینه | قانون مرز لایه‌ها (۰.۱) از اولین commit |
| تست‌های شکننده | تست unit بدون شبکه؛ رسانک برای هندلرها |
| مستندات کهنه | DoD شامل مستند؛ README نقشهٔ زنده |
